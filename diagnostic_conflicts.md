# Диагностика ZERKALO — 4. Конфликты и сводка находок

Диагностический отчёт (только чтение, изменения в код не вносились).
Часть 4 из 4: точки конфликта парсеров и ИИ, «двойные корзины», сводка находок.

## 4.1. Где парсер может перебить ИИ и наоборот

| # | Место | Кто побеждает | Правило |
|---|---|---|---|
| 1 | `app_state.dart:1208-1210` | **парсер** | Вся фраза с лидом заметки не уходит в ИИ: `local.note != null → return local`. ИИ даже не вызывается |

| 9 | `app_state.dart:1428-1435` | **парсер** | ≥2 дня рождения / ≥2 «N числа» → календарь полностью перезаписывается локальным списком |
| 10 | `app_state.dart:1522-1543` | **парсер** | `_keepRemoteCalendar` выкидывает модель, если день = сегодня, нет слова «сегодня/дня» и нет явного «другого дня» (это же правило на сервере — `keepServerCalendar`, `ai.ts:949-966`) |

## 4.2. Где один текст уходит в две корзины

1. **Заметка + трекер.** `splitNoteBody` (`note_intent.dart:223-272`): клаузы с лидом задачи → `taskClauses`, остальное → `note`; `_commitWave1` пишет обе сущности (`app_state.dart:1570-1581` и `:1599-1614`), итог — `InputKind.mixed` («Записано: заметки, задачи», `:1729-1744`). То же на сервере: `splitNoteBodyClauses` (`ai.ts:1899-1952`) + дедуп `clauseMentionsTitle` (`:1888-1898`, `:1928-1941`).
2. **Заметка + календарь.** Клаузы «другого дня» → `eventClauses` (`note_intent.dart:242-247`). **Исключение:** если в тексте есть «напомн…», дата остаётся сроком заметки, а не событием (`reminderLead`, `:97-99`, `:244`; на сервере то же — `ai.ts:1918-1922`).
3. **Календарь + трекер.** `skipOverlappingTasks` (`app_state.dart:1316-1321` и `:1474-1480`): если календарь непустой, а явного лида задач/списка нет — задачи не создаются. Плюс защита от одинаковых заголовков: `calendarTitles` вычитаются из задач (`:1337-1351`).
4. **Метрика + заметка.** Если в клаузе заметки нашлась карточка метрики — клауза уходит в метрику и из заметки исчезает (`note_intent.dart:258-261`). Если карточки нет — остаётся в заметке (и метрики не будет: `_saveStandaloneMetrics` вернёт `false`, `app_state.dart:3016-3017`).
5. **Метрика + трекер/календарь.** Метрики считаются по `work` (текст без предложений с лидом заметки, `app_state.dart:1259-1260`, `:1278`), а задачи/календарь — по `taskWork`/`calendarWork` (`:1262-1263`); значит одна фраза может дать метрику + задачу («Выпил 2 чая и сегодня нужно купить молоко» — прямо проверено тестом `test/ai_priority_test.dart:62-69`).
6. **Запись + строка истории.** `_logActivity` (`app_state.dart:1748-1790`) для каждой созданной записи добавляет нейтральный `LifeEvent` c `destination` в таблицу `events` → одна фраза = 2 строки в БД (в корзине и в ленте).
7. **`metrics` ↔ `daily_*`.** Опросы «Зеркала» (`daily_polls.mood/energy/stress/sleep/sport`) живут отдельно от `metric_values` — один и тот же показатель можно записать дважды разными путями.
8. **Граничные сценарии, где текст «пропадает»** (не корзина, а потеря): в `splitNoteBody`/`splitNoteBodyClauses` ветка `if (tasks.some(title => clauseMentionsTitle(...))) continue;` (`ai.ts:1941`) и `calendarTitles`/`metricNames` (`:1928-1935`) **выбрасывают** клаузу без записи в заметку. Т.е. если модель/парсер распознал из неё задачу-событие, но само распознавание затем отфильтровалось (например, `keepServerCalendar` отбраковал событие), текст исчезает из всех корзин.

## 5. Сводка находок (для приоритизации)

**Мёртвое / можно чистить:**
1. `achievements` — таблица + триггер `sync_event_achievement` + CHECK `events_achievement_weight_range` при живых дублях-колонках в `events`.
2. `input_sources` — никогда не наполняется (аудио идёт в Storage), но участвует в RLS, GRANT и удалении аккаунта.
3. `legal_documents` — только сид; тексты статические в `docs/` и `deploy/legal/`.
4. `v_metric_totals` — вьюха без единого потребителя.
5. Серверный путь `saveNotes`/`saveStandaloneMetrics` в `process_input.js` недостижим: клиент всегда `preview=true`, а `processRecording` не вызывается.
6. `metric_values_backup_dedup` — разовый бэкап (если чистка выполнена).
7. `age_years`/`age_bucket` — SQL-функции без вызовов.
8. Колонки `events.source_id`, `notes_reminders.sphere_id` (читается, но её нет), `metrics.sphere_id` (в типах сервера и модели клиента), `payments.payload`.
9. Три trgm-индекса (`events_text_trgm_idx`, `events_parsed_trgm_idx`, `notes_text_trgm_idx`) — кандидаты на удаление после проверки `idx_scan`.

**Расхождения, которые могут дать баги:**
1. Три словаря повторяемости (`notes_reminders` enum без `yearly`, `calendar_events` text без `none/daily`, клиентский `RepeatRule` с `yearly`).
2. `metric_values` без UNIQUE(`metric_id`,`date`) → повторные копии (уже два скрипта чистки).
3. `daily_answers` UNIQUE(`user_id`,`date`) при 365 вопросах — одна победа в день, остальные ответы теряются.
4. Заметки/календарь с клиента могут иметь `reminder_datetime`/`repeat_type` в комбинациях, которые серверный путь не поддерживает (`yearly` в enum отсутствует — серверный `saveNotes` глушит его в `'none'`, `process_input.js:300-306`).
5. Каждый ввод пишет 2+ строки (`events` + корзина) — «дублирование» в отчётах пользователя будет выглядеть как дубли.

**Конфликтная логика (по дизайну, но стоит знать):**
- Нет флага «ИИ ответил → парсеры не трогают»; 20 мест, где локальные парсеры перебивают модель (см. 4.1), из них 4 — «локальный ответ → ИИ не вызывается».
- Текст, вычтенный из заметки моделью/парсером (задачи/события/метрики), не возвращается назад, если соответствующая запись позже отбракована фильтрами — возможна потеря фразы.
